# DiLink-Auto

*Оригинал этого документа — [README на английском](../../README.md).*

Транслируйте приложения со своего телефона на встроенный экран автомобиля с полным сенсорным управлением. Открытый исходный код, сервисы Google не требуются.

Это **исходный репозиторий** DiLink-Auto ([andersonlucasg3/dilink-auto-android](https://github.com/andersonlucasg3/dilink-auto-android)). В ноябре 2026 года в него были обратно влиты 252 коммита долгоживущего форка [ID-VerNe/dilink-auto-android](https://github.com/ID-VerNe/dilink-auto-android), который поддерживал проект живым, пока upstream молчал. Разработка продолжается с фокусом на **китайские прошивки телефонов + головные устройства BYD DiLink**, с отдельной настройкой под **бюджетный DiLink 4.0**, чтобы он превратился из «слайд-шоу» в пригодный для использования на слабом железе.

## Что изменилось с v0.18.0-dev

Краткая версия эволюции между точкой форка (`84df5cb`, upstream/main) и текущим `main`. Каждый пункт соответствует реальным коммитам, а не планам; подробная хронология — в [docs/progress.md](../progress.md).

### 1. Архитектура прямого стриминга VD

Телефон больше не ретранслирует видео, касания и звук. VD-сервер привязывается к портам `9638` (видео), `9639` (ввод) и `9640` (звук, открывается после двусторонних переговоров) и общается с приёмником напрямую. Это убирает 4 сокета + 2 переключения контекста процесса на кадр, оставляя 2 сокета + 0 переключений контекста. Телефон становится чистым оркестратором: рукопожатие и согласование возможностей, жизненный цикл VD (`VD_PORTS_BOUND`) и маршрутизация логов головного устройства. В протокол добавлены `FrameCodec.readFrameBlocking()`, `MessageType.VD_PORTS_BOUND` и `AudioPayload`, а `VirtualDisplayClient` сведён только к жизненному циклу.

### 2. Настройка бюджетного DiLink 4.0 (основная работа)

Для указанного выше железа:

- **Размер кодирования ограничен 1920x1080.** Раньше телефон масштабировал VD до физических пикселей (1080x2340 → кодирование 2340x1658), чтобы избежать обрезки IME; это превышало предел аппаратного декодирования 439, приводило к программному декодированию, и 8x A53 тянули H.264 выше 1080p с однозначным fps. Исправлено разделением размера VD и размера кодирования — VD остаётся увеличенным (сохраняя исправление IME), а размер кодирования следует за вьюпортом, который сообщает автомобиль, и ограничивается 1920x1080.
- **Битрейт 8 Mbps → 4 Mbps.** Измеренная устойчивая пропускная способность в автомобильной среде 2,4 ГГц составила 5-15 Mbps, поэтому 8 Mbps не оставляли запаса. Адаптивный откат тоже подтянут: нижняя граница 1,5 Mbps, окно восстановления 2 с, шаг 0,5 Mbps (раньше он колебался между 8 и 2 Mbps).
- **Частота кадров 30 → 24 → 20.** По умолчанию теперь 20 fps (50 мс на кадр). См. issue #71: 2,5 ч навигации оставляли телефон горячим, а снижение частоты кадров — второй клапан сброса давления после потолка апскейла VD.
- **TextureView → SurfaceView.** Позволяет пропустить покадровую полноэкранную GL-композицию Adreno 505 (около 2-5 мс/кадр). Затвор `outputSurfaceValid` не даёт рендерить в уничтоженную поверхность, когда декодер скрывается/показывается при навигации.
- **Приоритеты потоков.** У A53 нет больших ядер, поэтому подсказки планировщику важны: потоки кодирования/декодирования/отвода сокетов используют `THREAD_PRIORITY_URGENT_DISPLAY`, `LifeWriter` — `THREAD_PRIORITY_BACKGROUND`.
- **Поведение логирования по умолчанию.** В release-сборках `carLogEnabled` по умолчанию выключен (раньше был включён, и кадры логов конкурировали с видео за канал 2,4 ГГц); `ConcurrentLinkedQueue.size()` (O(n)) заменён на `AtomicInteger`.
- **Очистка AppIconCache при отключении.** Около 80-150 PNG бесконечно накапливались на 16 ГБ eMMC (5-9 МБ кучи). Новый `clear()` вызывается из `handleDisconnect`, а `prepareAll` декодирует параллельно с `Semaphore(4)`, перерабатывая промежуточные bitmap.
- **Удалён `Debug.getPss()`.** Этот устаревший binder-вызов выполнялся при каждом подключении и стоил 100-500 мс на A53; теперь он собирается только при падении.
- **`@Immutable AppTileData`.** `AppInfo` несёт `ByteArray`, из-за чего `AppTile` становился non-skippable и при любом переприсваивании `appList` выполнялась полная перекомпозиция. Неизменяемая обёртка, исключающая `iconPng`, позволяет сетке пропускать перекомпозицию.

### 3. Совместимость с головными устройствами API 28

На реальном устройстве BYD (`k65v1_64_bsp`, Android 9 / API 28) `MediaCodecInfo.isHardwareAccelerated()` (API 29+) выбрасывает `NoSuchMethodError` и убивает процесс. Спекулятивный выбор аппаратного декодера удалён, а `createDecoderByType` восстановлен (`REGULAR_CODECS` и так ставит аппаратные декодеры первыми; на BYD выбирается `OMX.qcom.video.decoder.avc`). `minSdk` повышен с 24 до 26 для `app-server` и `protocol`, а lint-затвор NewApi снова включён. `am display move-stack` (API 29+) теперь под условием `SDK_INT` для API 26-28 и пишет лог вместо того, чтобы считать сбой shell успехом.

### 4. UI и взаимодействие

- **Редизайн панели навигации:** сведена к Извлечь (отключение) / Домой / Назад. Кнопка уведомлений, панель недавних, часы и информация о сети удалены вместе с мёртвым кодом в четырёх модулях (на стороне авто `NotificationScreen`, `RecentAppsState`; на стороне телефона `NotificationService`; типы сообщений `FOCUSED_APP` / `APP_SHORTCUTS` / `NOTIFICATION_*`). **Пересылки уведомлений в этой кодовой базе нет.**
- **Закрепление приложений:** долгое нажатие на иконку приложения даёт «Закрепить сверху» / «Открепить», сохраняется в SharedPreferences.
- **Белый список приложений:** новый `AllowlistScreen` позволяет пользователю выбрать, какие приложения передаются в автомобиль; невыбранные отфильтровываются в `sendAppList`, уменьшая полезную нагрузку по сети и работу декодирования иконок на авто. Популярные навигационные приложения выбраны заранее при первом запуске. Переключение отправляет `ACTION_ALLOWLIST_UPDATED`, чтобы работающий сервис заново отправил список и сетка на авто обновилась на лету.
- **Поддержка приложений в портретной ориентации:** динамический расчёт DPI (`VideoConfig.calculateOptimalDpi`) не даёт портретным приложениям (Amap, WeChat) сжиматься в узкую полосу внутри ландшафтного VD; IME восстанавливается по завершении сессии (раньше телефон оставлял себе клавиатуру linkpc); исправлен индекс инъекции мультитача.
- **Переопределение стартового DPI на стороне авто:** в рукопожатие добавлено поле `dpiOverride` (0 = автоматически, [120, 480] = значение пользователя), управляемое настройкой `startup_dpi` автомобиля и отправляемое для обеих ориентаций. Исправляет слишком маленький DPI по умолчанию на 1280x800.
- **Токены цвета и выравнивание типографики:** разбросанные `Color.Gray` / `0xFF888888` перенесены в `onSurfaceVariant`, дублирующиеся красные ошибки объединены, подписи 12sp → 14sp. «WiFi Direct Mode» переименован в «WiFi ADB Mode»; текст `adb tcpip` на стороне авто удалён.
- **Исправление чёрного экрана при повороте:** `onCarViewportChanged` при повороте переводит состояние в CONNECTING и заново разворачивает VD, но затвор раскладки стриминга использовал `isConnected` (false в течение ~2 с повторного развёртывания), поэтому `CarShell` откатывался на `CarLaunchScreen`, `TextureView` покидал композицию и новая поверхность не могла перезапустить декодер. Теперь затвор также принимает `state == CONNECTING && appList.isNotEmpty()`, сохраняя раскладку стриминга (и её оверлей ожидания видео) во время поворота.

### 5. Стабильность сессии

Активная сессия никогда не уничтожается попыткой переподключения — раньше повтор через шлюз Wi-Fi или ручное подключение могли убить работающую сессию. Цикл переподключения останавливается после 3 подряд сбоев ADB. ADB по TCP переподключается при смене IP телефона и автоматически откатывается к TCP ADB, когда USB недоступен.

### 6. Стабилизация PipelineServer

`VirtualDisplayServer` (1287 строк, 9 потоков, 2 очереди) стал `PipelineServer` (один поток, 0 очередей): такт кадров → рендер GL → отвод энкодера → запись в TCP, с естественным управлением потоком (застрявшая запись TCP блокирует следующий `eglSwapBuffers`). Также исправлено: GL-текстура, созданная во временном контексте EGL и затем уничтоженная (поток конвейера привязывал текстуру 0); `app_process` убивался при выходе неинтерактивного shell (исправлено через `shellBackground`, который удерживает поток shell присоединённым); и порядок восстановления физической панели (раньше `input keyevent 224` вызывался уже после закрытия shell).

### 7. Переключатель диагностического лога

Настройки → Отладка получили переключатель диагностического лога. Когда он выключен, записей на диск нет. Состояние передаётся в автомобиль через data-сообщение `LOG_TOGGLE` и с issue #72 также автоматически синхронизируется после каждого рукопожатия, чтобы лог авто следовал за переключателем телефона, а не тихо сбрасывался при переподключении. Значения по умолчанию: включён для debug/пре-релиз сборок, выключен для release; явный выбор пользователя сохраняется.

### 8. Упрощённый китайский интерфейс

И клиент, и сервер поставляются с `values-zh-rCN` / `values-zh`. Строки приложения есть на английском, португальском (BR), французском, русском, белорусском, казахском, украинском, узбекском и китайском.

### 9. Здоровье кода

Несколько раундов аудита и рефакторинга по SRP/DRY: общие константы между модулями (`AppPrefs`, `AppTargets`, `VdDeploy`, `VdDeployArgs`, `WifiGatewayIp`, `AppIconLimits`) и выделенные коллабораторы.

- **`protocol-core` / `protocol`:** `NioWriter` (запись в канал сокета со спин-ожиданием и таймаутом), `BackoffPolicy` (параметризованный экспоненциальный откат), `DecodeLivenessTracker`, `ConnectionFactory`, `ConnectionKeepAlive`, `UsbAdbKeyStore`, `Ipv4Validator`, `AppIconLimits`; мёртвый код `UsbAdbConnection` удалён.
- **`vd-server`:** `AsyncSocketSender`, `AudioEncoderSelector`, `ProcessWatchdog`, `VideoEncoderSelector`, `PortAcceptor`, `ActivityDumpParser`, `VdDisplayHealer`.
- **`app-client`:** `ConnectionService` ужат; выделены `ShizukuVdDeployer`, `ShizukuNav`, `ClientNetworkMonitor`, `CarAppInstallHost`, `AllowlistRepository`, `SessionState`; `InputInjectionService` объявлен устаревшим.
- **`app-server`:** `CarConnectionService` сокращён до ~407 строк; машина состояний разделена на `CarSessionCoordinator` (многоканальная машина состояний 9637/9638/9639/9640 и повторное рукопожатие), `CarAdbTracker` (отслеживание USB/TCP ADB) и `CarAppListReceiver` (список приложений и лимиты безопасности иконок).
- **`app-desktop`:** использует `AppIconLimits`, `DecodeLivenessTracker`, `BackoffPolicy`, приведён в соответствие с последними примитивами протокола.

### 10. Исправление утечки VD, идемпотентная очистка, самовосстановление после чёрного экрана

**Первопричина:** каждое переподключение утекало один VirtualDisplay. Старый код использовал `pkill -9`, который пропускает shutdown-хук JVM, поэтому `PipelineServer.cleanup()` не выполнялся — VD не освобождался, физическая панель оставалась выключенной, а настройка `screen_off_timeout` терялась (снимок фиксировал сентинел `2147483647`, который записал сам код). Через несколько переподключений экран авто становился чёрным.

**Исправление (12 файлов):** сентинел запроса остановки (`/sdcard/DiLinkAuto/stop-request`), который потребляет сторож движка, чтобы выйти штатным путём и выполнить полный `cleanup()` (ART не выполняет shutdown-хуки при голом SIGTERM); проверка на основе `pgrep -f` (toybox отвергает `pkill -0`); откат `kill -9`, который находит pid через `pgrep -f`, а не `pkill -f` (последний также убивает обёрточный shell и делает результат ADB нечитаемым); `cleanupGuard` на `AtomicBoolean`, чтобы 7 мест вызова не выполняли `cleanupSession()` повторно (одно отключение вызывало 9 вызовов «Force-waking physical display»); `waitForVdServerExit()` с обеих сторон, чтобы два движка никогда не боролись за один VD и порты; `PhoneDisplayRestorer` в собственной области жизни процесса с `NonCancellable`; переупорядоченный `cleanup()`; валидация значения в `DisplayPowerController.restoreSetting()`; и `BlackScreenDetector` (`BLACK_SCREEN_SUSTAIN_MS = 3000`), перенесённый в `protocol-core`, чтобы авто и desktop делили его, а `rehandshakeForBlackScreen()` ограничен не более чем одной попыткой на сессию.

Автоматизация регрессий живёт в `scripts/`: `verify-blackscreen-fix.sh`, `e2e-reconnect-cleanup.sh`, `verify-reconnect-cleanup.sh` (32 проверки, прогоняемые через реальный UI desktop; последний полный прогон 32/32, 2m48s).

### 11. Приёмник Windows `:app-desktop`

Помимо головного устройства, тот же протокол поддерживает **программу для Windows** в роли приёмника: экран телефона транслируется в окно ПК, а мышь становится касанием. Модуль находится в `app-desktop/` (Kotlin/JVM + Compose Desktop 1.6.2, JDK 17) и переиспользует `protocol-core` — без изменений на стороне телефона.

- **Транспорт:** три TCP-соединения напрямую к телефону — 9637 (управление + данные), 9638 (видео), 9639 (ввод) — как и в авто, без ретрансляции.
- **Разделение развёртывания:** `connectionMethod` в ответе рукопожатия решает, кто разворачивает VD-сервер. С Shizuku это делает телефон; иначе desktop разворачивает локальным `adb.exe` (`connect` → убить старый движок **и дождаться его реального выхода** → `exec app_process`), для чего нужен `"dev_mode": true` в `config.json`.
- **Декодирование:** программное декодирование JavaCV/FFmpeg плюс аппаратное D3D11VA, с автоматическим откатом, когда аппаратное падает на старте или выдаёт ноль кадров.
- **UI:** три страницы навигации — Зеркало / Приложения (лаунчер) / Дисплей (переопределение DPI, переключатель аппаратного декодирования, «Применить и переподключиться», не давать засыпать, физический экран телефона).
- **Самовосстановление:** 10 с устойчивого чёрного экрана вызывают автоматическое переподключение, не более двух раз на процесс.
- **Конфиг и логи:** `%APPDATA%\DiLinkAuto` (`config.json` / `desktop.log`), переопределяется через `DILINK_DESKTOP_HOME`; `DILINK_ADB` задаёт путь к adb.

```bash
# Самодостаточный образ приложения (встроенный JRE): копия build/compose/binaries/main/app/DiLinkAuto
./gradlew :app-desktop:createDistributable

# Headless-проверка: валидирует только рукопожатие/VD/fps; без Shizuku задайте DILINK_DEV_MODE=1 для развёртывания через ADB
app-desktop --probe
```

> Статус: путь через Shizuku совпадает со стороной авто; **путь развёртывания через ADB ещё не проверен на реальном устройстве**. Модуль не входит в релизные ассеты (его зависимость JavaCV/FFmpeg под GPL, тогда как проект под MIT).

### 12. Юнит-тесты и усиление безопасности

**Покрытие тестами:** у двух модулей вообще не было набора тестов (`vd-server` не имел `src/test`, у `protocol` он был пуст). Начиная с `8157c86` юнит-тесты JUnit4 были добавлены во все 6 модулей, покрывая самую рискованную ранее непротестированную логику (фрейминг протокола, криптографические примитивы ADB, аргументы развёртывания VD, адаптивный битрейт, затвор квотирования shell, затворы версий, классификацию статуса установки, формат отчёта о падении). Дополнительный раунд сохраняющих поведение «швов тестируемости» добавил ещё 44 случая. Сегодня в репозитории более 1 200 случаев `@Test` в 6 модулях (JUnit4 + kotlinx-coroutines-test, без Robolectric/Mockito/MockK; Android-модули используют `isReturnDefaultValues=true` с рукописными фейками). Инвентарь, зафиксированные межмодульные инварианты и открытые вопросы — в [docs/IMPLEMENTATION_REPORT_TESTING.md](../IMPLEMENTATION_REPORT_TESTING.md).

**Усиление доверия к пирам (`a7d2b72`):** раньше любой сетевой пир считался доверенным — искажённый кадр в 6 байт мог убить процесс телефона или VD-сервер под shell-UID. Все пять декодеров теперь проверяют через `require()` перед сырыми `getX()`; корутины чтения ловят `Throwable`, логируют причину и отключаются вместо падения; `MAX_PAYLOAD_SIZE` уменьшен со 128 МБ до 16 МБ, а буфер `NioReader` имеет жёсткий предел, освобождаемый на границах кадров.

**Авторизация канала VD (`8601fb1`):** порты 9638/9639 принимали любой хост в той же Wi-Fi сети, позволяя кому угодно инжектировать касания и выполнять `am start` / `pm uninstall` как shell. Теперь они принимают только подключения от приёмника, который обслуживается в данный момент; отклонённые пиры закрываются, а сервер продолжает ждать.

**Квотирование shell (`5eae3e7`):** командные строки `VdDeploy` проходят через `shellQuote`, поэтому строки, контролируемые пиром, никогда не попадают в `sh` в сыром виде.

**Desktop (`1f6836a`):** `adbPort` / `jarPath` из ответа рукопожатия проверяются перед использованием (раньше они передавались прямо в развёртывание, то есть произвольное выполнение кода от любого пира); дочерние процессы adb больше не утекают.

**Сессия авто (`bc2634c` / `35d7821`):** сессии используют защёлку поколения, чтобы `cleanupGuard` не расходовался слишком рано путём смены сети; восстановление после чёрного экрана больше не вызывает `stop()` у декодера (никто его не перезапускал, поэтому путь восстановления гарантировал постоянный чёрный экран).

**Цепочка поставок релиза:** release-keystore раньше был закоммичен; теперь он только упоминается, а секреты подписи хранятся в CI (историю git ещё нужно очистить). CI больше не запускает код PR на self-hosted раннерах (`9517205`) и не производит неподписанные / чрезмерно обрезанные APK и осиротевшие артефакты (`efde81f`). Все workflow работают на GitHub-hosted `ubuntu-latest`.

## Текущий статус функций

**Работает:**

- Зеркалирование видео H.264, 20 fps по умолчанию, CBR 4 Mbps, профиль Main (настроено под бюджетный DiLink 4.0; работает и на старших устройствах)
- Зеркалирование звука: AAC-LC 48 кГц стерео на 128 kbps по выделенному TCP-соединению (9640), джиттер-буфер 150 мс, постоянное заполнение тишиной на 46,875 fps, двустороннее согласование возможности `FEATURE_AUDIO`, сохраняемый переключатель звука на клиенте
- Полный сенсорный ввод (мультитач, пинч-зум)
- Лаунчер приложений: поиск, алфавитный порядок, иконки 64dp, меню по долгому нажатию (удалить, сведения о приложении, закрепить)
- Белый список приложений: в автомобиль передаются только выбранные приложения
- Переопределение стартового DPI на стороне авто (исправляет маленький DPI по умолчанию на 1280x800)
- Следование ориентации: VD пересоздаётся при повороте авто, портретные приложения больше не сжимаются в полосу
- Поддержка Shizuku: развернуть VD-сервер без USB ADB и самостоятельно обновить приложение авто тихим `pm install`
- Самообновление приложения авто: телефон сравнивает `versionCode` и обновляет приложение авто по Wi-Fi ADB
- Экран телефона выключен во время стриминга (экономит батарею); физическая панель восстанавливается при отключении
- Пошаговое знакомство с разрешениями
- Упрощённый китайский интерфейс плюс ещё 8 языков интерфейса
- Архитектура прямого VD: без ретрансляции на телефоне; видео, касания и звук идут напрямую
- Исправление утечки VD: штатная остановка через сентинел (полный `cleanup()`, `kill -9` только как откат по таймауту), идемпотентный затвор очистки, ожидание выхода VD
- Самовосстановление после чёрного экрана: авто пересоздаёт VD (повторное рукопожатие) после 3 с устойчивого чёрного экрана; приёмник Windows использует тот же детектор с окном 10 с
- Приёмник Windows (`app-desktop`): окно зеркала, сенсор мышью, лаунчер приложений, панель DPI/аппаратного декодирования, развёртывание через adb, app-image `jpackage`

**Удалено (относительно upstream до слияния):**

- Пересылка уведомлений (уведомления телефона → экран авто): кнопка уведомлений на панели навигации, список уведомлений и протокольные сообщения `FOCUSED_APP` / `APP_SHORTCUTS` / `NOTIFICATION_*` удалены
- Панель недавних, часы, информация о сети

**Не реализовано:**

- Управление медиа
- Навигационные виджеты (зеркалирование звука полностью готово)

**Известные ограничения:**

- Для работы USB ADB нужно отключить Samsung Auto Blocker (Настройки → Безопасность → Auto Blocker → выключить).
- Управлению батареей Samsung требуется явное исключение.
- Samsung Knox может показать запрос безопасности при первом обращении к виртуальному дисплею.
- Точку доступа телефона нужно включать вручную (ограничение Android 16).
- Возможны редкие визуальные артефакты из-за гонки при перезапуске декодера; следующий ключевой кадр (~1 с) восстанавливает картинку.
- Задержка стриминга составляет примерно 100-200 мс под нагрузкой.
- Некоторые приложения не заполняют экран (letterbox / только портрет). DiLink-Auto зеркалирует ландшафтный виртуальный дисплей, поэтому приложения, не поддерживающие ландшафт, показывают чёрные полосы — это решает само приложение.
- На устройствах API 26-28, если рефлексия `DisplayControl` не удаётся, shell-откат `cmd display power-reset` / `power-off` тоже требует API 29+, поэтому физическая панель может не вернуться (вместо тихого отказа пишется лог).
- Прогресс установки не отображается на языках интерфейса, кроме английского: `InstallStatus.parse` классифицирует локализованные строки статуса по английским подстрокам, поэтому китайский (и другие) попадают в `IDLE`. Зафиксировано тестами, не исправлено ([C-6](../IMPLEMENTATION_REPORT_TESTING.md)).
- Первую установку приложения авто можно было пропустить с экстремальным номером версии: `readInstalledVersion` возвращает `"0"`, когда приложения авто нет, поэтому встроенный `versionName` `0` / `0.0` / `0.0.0` сравнивается как «актуально». Текущий `versionName` — `0.19.0`, поэтому это не срабатывает ([C-5](../IMPLEMENTATION_REPORT_TESTING.md)).

## Как это работает

1. **Включите точку доступа** — включите Wi-Fi точку доступа телефона; автомобиль подключится к ней.
2. **Подключите** — подключите телефон к USB-порту автомобиля (или войдите в ту же Wi-Fi сеть).
3. **Автоустановка** — телефон устанавливает приложение авто по Wi-Fi ADB (только в первый раз, одно нажатие).
4. **Автоподключение** — четыре TCP-потока по Wi-Fi: управление (9637), видео (9638), касания (9639), звук (9640, открывается после согласования).
5. **Пользуйтесь приложениями** — запускайте любое приложение из лаунчера авто; оно работает на телефоне, появляется на экране авто и принимает касания.

Телефон запускает приложения на виртуальном дисплее и кодирует их в H.264, который передаётся в автомобиль. События касания с экрана авто инжектируются обратно в телефон как настоящие события касания. Физический экран телефона остаётся выключенным для экономии батареи и сохраняет независимую работоспособность.

Архитектура, поток подключения и проектные решения: [docs/architecture.md](../architecture.md).

## Требования

**Телефон:**

- Android 10+ (`minSdk = 29`)
- Включённая отладка по USB (Параметры разработчика)
- Разрешение доступа ко всем файлам (пошагово при первом запуске)

**Автомобиль:**

- BYD DiLink 3.0+, проверено на **BYD Qin PLUS DM-i 2023 Champion 55KM Leading** (бюджетный DiLink 4.0, Snapdragon 439 / Android 9 / 1280x800)
- Android 8.0+ (`minSdk = 26`)
- Один свободный порт USB-A (или та же Wi-Fi сеть)

**Точка доступа телефона должна быть включена** — автомобиль подключается к ней. Без кодов сопряжения и без аккаунта Google.

**Подключение к интернету не требуется.** DiLink-Auto передаёт поток локально через точку доступа телефона; телефон и автомобиль общаются напрямую. Интернет нужен только приложениям, работающим на вашем телефоне.

## Установка

Скачайте APK из [Releases](https://github.com/andersonlucasg3/dilink-auto-android/releases/latest) или соберите его сами:

1. **Сборка:** `./gradlew :app-client:assembleDebug`
2. **Установка на телефон:** `app-client/build/outputs/apk/debug/app-client-debug.apk`
3. **Включите отладку по USB** (Настройки → Параметры разработчика)
4. **Откройте DiLink-Auto** и пройдите знакомство с разрешением доступа ко всем файлам
5. **Включите точку доступа и подключите к автомобилю** — приложение авто устанавливается автоматически при первом запуске по Wi-Fi ADB

APK автомобиля и JAR VD-сервера упакованы в APK телефона, поэтому на автомобиль ничего не нужно устанавливать отдельно, а установка приложения авто не требует интернета.

> **Замечание об обновлении подписи:** переход с debug-подписанной сборки на официально подписанную меняет сертификат — **сначала удалите старый пакет**, иначе установка завершится с `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. Полные правила релиза и подписи: [docs/release.md](../release.md).

## Структура проекта

APK телефона (`app-client`) встраивает APK автомобиля (`app-server`) и JAR VD-сервера (`vd-server`). Приёмник заменяем: тот же протокол работает на автомобиле (`app-server`) или на Windows (`app-desktop`).

```
DiLink-Auto/
├── protocol-core/  Чистая JVM-библиотека (frames, messages, константы, последовательность развёртывания VD; без зависимости от Android)
├── protocol/       Адаптация платформы (ADB, хуки Android, соединения USB/TCP)
├── app-client/     APK телефона — оркестрация, развёртывание VD, самообновление авто, белый список приложений
├── app-server/     APK авто — UI, машина состояний подключения, видеодекодер
├── app-desktop/    Приёмник Windows — окно зеркала, декодирование FFmpeg, развёртывание adb, jpackage
├── vd-server/      Сервер VirtualDisplay (компилируется в JAR, разворачивается телефоном)
├── scripts/        Автоматизация (проверка логов, сквозное переподключение/очистка)
├── docs/           Документация (многоязычная точка входа)
└── gradle/         Система сборки
```

| Модуль | Роль | minSdk |
|--------|------|--------|
| `protocol-core` | Чистая JVM-библиотека протокола (Connection/NioWriter/NioReader/FrameCodec/Messages/AudioPayload/VdDeploy/BackoffPolicy/DecodeLivenessTracker/BlackScreenDetector) | — |
| `protocol` | Общая библиотека протокола (UsbAdbConnection, AdbProtocol, VideoConfig, ConnectionFactory, ConnectionKeepAlive, UsbAdbKeyStore) | 26 |
| `app-client` | Приложение телефона (ConnectionService, ShizukuVdDeployer, ClientNetworkMonitor, CarAppInstallHost, AllowlistRepository, FileLog) | 29 |
| `app-server` | Приложение авто (CarSessionCoordinator, CarAdbTracker, CarAppListReceiver, AudioPlayer, VideoDecoder, CarShell, HomeScreen, PersistentNavBar) | 26 |
| `app-desktop` | Приёмник Windows (DesktopApp, DesktopConnectionService, VideoDecodePipeline, SwingVideoView) | — |
| `vd-server` | Процесс под shell-UID (PipelineServer, AudioPipeline, AudioEncoderSelector, PortAcceptor, TouchInjector, GlPipeline, DisplayPowerController) | — |

## Сборка

```bash
# Собирает APK телефона (запускает buildVdServer + embedServerApk, упаковывая vd-server.jar и app-server.apk в ассеты клиента)
./gradlew :app-client:assembleDebug

# Расположение APK:
# app-client/build/outputs/apk/debug/app-client-debug.apk  (телефон, встраивает APK авто)

# Юнит-тесты (6 модулей, JUnit4 + kotlinx-coroutines-test, без Robolectric/Mockito/MockK)
./gradlew :protocol-core:test :protocol:test :vd-server:test :app-desktop:test
./gradlew :app-client:testDebugUnitTest :app-server:testDebugUnitTest
```

Требуются JDK 17 и Android SDK (compileSdk 34). Для release-сборок нужны `RELEASE_KEYSTORE_PASSWORD` / `RELEASE_KEY_PASSWORD` (`RELEASE_KEYSTORE_FILE` / `RELEASE_KEY_ALIAS` опциональны); отсутствие обязательной переменной приводит к сбою на этапе конфигурации вместо тихой сборки неподписанного APK, который нельзя установить поверх официального. Сам keystore никогда не коммитится.

В Windows эквивалентные команды используют `.\gradlew.bat`.
